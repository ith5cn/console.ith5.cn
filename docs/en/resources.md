# Design: resource kinds and levels

> Status: final (2026-09-10). Aligned with teamai-cli's resource formats and the #341 level model.

## 1. How teamai shapes resources

| Shape | Resources |
|---|---|
| Multi-file directory | skill (directory with `SKILL.md`) |
| Single file or single record | rule (`rules/*.md`), doc (`docs/**`), agent (`agents/<name>.yaml`), claudemd fragment, one MCP server, one hook declaration, one env variable |
| One per level | `culture.md`, the `sharing` block of `teamai.yaml` |

Not resources: `tags.yaml` (tags on resources), `manifest/roles.yaml` and `manifest/projects.yaml`
(generated by the server), `sources` (not supported).

## 2. Kinds

| kind | shape | notes |
|---|---|---|
| `skill` | directory | commands are merged into skills |
| `rule` | single markdown | |
| `doc` | single file, sub-paths allowed | name is the relative path, e.g. `arch/overview.md` |
| `agent` | YAML spec | teamai's YAML is canonical; rendered per tool on the way out |
| `hook` | one declaration + optional script | id / event / matcher / command / timeout |
| `mcp` | one server definition | name / transport / command / args / url / headers / env / timeout |
| `env` | one variable | name is the KEY; one variable per resource |
| `claudemd` | markdown fragment | injected into CLAUDE.md / AGENTS.md |
| `culture` | singleton | name fixed to `culture` |
| `policy` | singleton | the `sharing` block: rules.enforced, hooks.autoApply / requireTeamScripts, mcp.allowedCommands / allowedHosts, recall.enabled, contributeHint.enabled, coAuthor.enabled |
| `learning` | single markdown | see knowledge.md |

Resource key: `(level, owner_id, kind, name)`. Any kind can carry `tags text[]`, returned as-is so the
client can filter by personal subscriptions.

## 3. Levels

```
org  →  team  →  project      (no user level in this phase)
```

A project may belong to a team or hang directly off the organization. `bundles.level` is an enum
`(org, team, project)` with `team_id` / `project_id` set according to the level.

## 4. Resolution

For a binding (user × device × projects), the entitled set is computed as:

1. All org-level resources.
2. Team-level resources of the teams that own the bound projects.
3. Project-level resources of the bound projects.
4. Resources granted through permission groups (§5).
5. For the same `(kind, name)`, the most specific level wins: project > team > org > group.
   A tombstone at a lower level masks the parent's resource; removing the tombstone restores it.
6. Two bound projects at the same level with different versions of the same name: the snapshot marks
   the key `conflict`; the client keeps its previous copy and does not guess.
7. `policy` is not overridden but merged field by field toward the stricter value:
   - `rules.enforced`: union; a lower level cannot remove parent entries.
   - `hooks.autoApply`, `mcp.autoApply`: if the parent says false, a child cannot say true.
   - `mcp.allowedCommands` / `allowedHosts`: when the parent is non-empty the child must be a subset.
   - `recall.enabled`, `contributeHint.enabled`, `coAuthor.enabled`: child may override.
8. `culture`: the most specific level's copy, never merged.

Personal exclusions, tag subscriptions, and local env overrides stay on the client.

## 5. Where permission groups fit

| Mechanism | Decides | teamai equivalent |
|---|---|---|
| Level placement | who **must** receive: org level everyone, team level team members, project level project members | project namespaces in `manifest/projects.yaml` |
| Permission group + assignment | who **additionally** receives: named optional bundles granted to users / projects / the org, optionally expiring | `manifest/roles.yaml`: one group = one role |

A resource placed in any permission group is no longer distributed by level; it is delivered only through
assignments. Otherwise an org-level resource inside a group would reach everyone and the group would be
meaningless. Group resources have the lowest priority during resolution.

## 6. Generated compatibility view

The server renders these per binding and the client reads them as if they were repository files:

| File | Generated from |
|---|---|
| `teamai.yaml` | merged policy + fixed toolPaths |
| `manifest/projects.yaml` | bound projects |
| `manifest/roles.yaml` | permission groups granted to the user |
| `tags.yaml` | tags of the resources in the snapshot |
| `skills/<ns>/<name>/`, `claudemd/<ns>/*.md` | ns = project slug or group key; org level uses `common` |
| `rules/`, `docs/`, `agents/`, `env/env.yaml`, `hooks/hooks.yaml`, `mcp/mcp.yaml`, `culture.md` | the corresponding kinds after resolution |

These files are views only and are never used as authorization input.
