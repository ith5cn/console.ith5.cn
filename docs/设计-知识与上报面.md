# 设计：知识（learnings）与上报面

> 状态：已定稿（2026-09-11）。对齐 teamai-cli 的 learnings / votes / sessions / stats 数据与
> issue #341 的"发布面 / 上报面"分离原则。
> 配套：[设计-变更集与发布.md](./设计-变更集与发布.md)、[设计-同步协议.md](./设计-同步协议.md)。

## 1. teamai 上报什么

| 数据 | 内容 | 自然语言 |
|---|---|---|
| learnings | 员工用 `/teamai-share-learnings` 让 AI 写的经验文档，frontmatter 含 title / author / date / tags，正文 Markdown | **有**，员工有意分享的知识 |
| votes | 每篇知识被召回次数、点赞次数、时间戳；客户端按增量同步 | 无 |
| sessions | 每次会话：工具序列、轮次、干预次数、时长、是否有价值；首条提示词一行为可选项 | 默认无 |
| stats | 每人每天：会话数、成功数、纠偏数、token、估算成本；skill 使用次数 | 无 |
| members | 花名册 | 无 |

## 2. learnings 走发布面

learning 本质是内容：要版本、按项目隔离、可归档、可晋升、要随 snapshot 下发给同项目成员做 recall。
因此 **learning 是一种资源 kind**，走变更集流程。

| 项 | 规则 |
|---|---|
| kind | `learning`，单文件 md，name 为 `<title-slug>-<date>-<random>`（沿用 teamai 命名） |
| 层级 | org 级（全员共享）或 project 级（项目私有），对应 teamai 的 `learnings/` 与 `learnings/<project-id>/` |
| 权限 | 单独一档 `learning:contribute`，普通成员默认拥有，不需要 `resource:write` |
| 发布 | **直接发布**：`teamai contribute` = 创建只含一条 `put learning` 的变更集并立即 fast_track 发布，记录完整审计 |
| 编辑 / 归档 | 作者可改、可归档自己的；管理员可归档任何。归档 = 发布 tombstone |
| 密钥扫描 | 服务端对内容跑密钥模式扫描（token、私钥、连接串、Bearer、`key=value` 形态）。**命中即拒绝**，返回命中位置与类型，让作者修改后重交。不自动打码 |
| supersedes | contribute 携带 `supersedes[]` 时，同一变更集内对被取代的 learning 发布 tombstone |
| recall | 客户端本地检索，服务端只负责下发。后台搜索用 PostgreSQL 全文检索（tsvector），不做 BM25、不做代码图谱 |
| 晋升 | 后台"晋升"= 创建变更集，把 learning 内容作为 skill / rule / doc 的 `put`，走正常审核 |

## 3. 上报面：三种计数数据

统一入口：

```
POST /v1/reports/events
  {device_id, events: [{event_id, seq, type, occurred_at, payload}]}
  type ∈ vote_delta | session_summary | usage_daily | skill_usage | tool_use
  → 按 (device_id, event_id) 去重；seq 为每设备单调序号
  ← {accepted: [event_id…], max_seq}
```

`tool_use` 即现有 `execution_events`，并入同一入口，表结构不变。

| type | 表 | 规则 |
|---|---|---|
| vote_delta | `knowledge_votes(user_id, resource_id, recalled_count, upvoted_count, last_recalled_at, last_upvoted_at)` | 增量累加；同一 event_id 不重复加 |
| session_summary | `sessions(id, org_id, user_id, device_id, session_id, tool, started_at, duration_ms, prompt_turns, tool_total, tool_sequence text[], interventions jsonb, tokens jsonb, valuable bool)` | 见 §4 隐私规则；同 session_id 的后续事件替换而非累加 |
| usage_daily | `usage_daily(user_id, day, sessions_ended, sessions_succeeded, prompt_turns, duration_ms, sessions_corrected, priced_requests, cost_micros, cache_read_tokens, cache_eligible_input_tokens)` | 按 (user_id, day) upsert；修正事件引用原 session_id，替换不累加 |
| skill_usage | `skill_usage(user_id, skill, count, last_used_at)` | 累加 |

去重账本 `report_events(device_id, event_id, seq, received_at)` 保留期覆盖最长离线窗口（30 天）；
超期的 event_id 返回 `410 EVENT_WINDOW_EXPIRED`，客户端不得换新 ID 重发。

## 4. 隐私规则（L0 禁运清单，服务端强制）

以下字段**无论客户端是否发送，服务端一律丢弃后再入库**：

- 会话摘要中的首条提示词一行（`promptSummary` / 任何 prompt 文本）
- `stoppedOutput`（AI 输出片段）
- `transcriptPath` 及任何本机绝对路径
- 文件内容、diff、完整命令行

保留的只有：工具名、计数、时长、token、时间戳。
README 中"审计的是工具调用，不涉及和 AI 的对话内容"这一承诺不变。

learnings 是员工有意撰写并分享的内容，不在禁运之列，但受 §2 的密钥扫描约束。

## 5. 置信度

由 votes 计算，用于知识库维护与健康度：

```
confidence = clamp( (upvoted_count + 1) / (recalled_count + 2) * age_decay, 0, 1 )
age_decay  = 0.5 ^ (months_since_last_recall / 6)
```

- 低于 0.15 且发布超过 90 天 → 后台"待归档"列表（对应 `recall maintenance --prune`）。
- 高于 0.7 且 recalled ≥ 5 → 后台"可晋升"列表（对应 `recall promote`）。
- 阈值组织级可配。

## 6. 后台页面

| 页面 | 数据来源 | 对应 teamai |
|---|---|---|
| 知识库 | learning 资源 + votes + 置信度；浏览、全文搜索、归档、晋升 | `recall`、`recall promote`、`recall maintenance` |
| 周报 | `usage_daily` + `sessions` 按周聚合，与前 7 天对比 | `digest` |
| 知识库健康 | 各 kind 数量、高频召回 top N、从未召回的沉默条目、按作者贡献、召回趋势 | dashboard → KB Health |
| 成员用量 | 每人会话数、纠偏率、token、成本估算 | `stats/` |

## 7. 保留期

| 数据 | 保留 |
|---|---|
| sessions、usage_daily | 13 个月 |
| knowledge_votes | 不过期 |
| report_events 去重账本 | 30 天 |
| tool_use | 沿用现有策略 |
