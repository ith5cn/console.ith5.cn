# 设计：Revision 与同步协议

> 状态：已定稿（2026-09-11）。对齐 issue #341 / PR #481 的 snapshot 语义，去掉增量游标。
> 配套：[设计-变更集与发布.md](./设计-变更集与发布.md)、[设计-资源类型与层级.md](./设计-资源类型与层级.md)。

## 1. 核心思路

**每次都给完整清单，内容按文件哈希取，revision 就是清单的哈希。**

- 清单很小（一个人几百条，几十 KB），不值得做增量。
- 内容按 sha256 取，客户端本地已有的一律不下载。跨版本去重、零下载回滚都由此而来。
- revision 由清单内容导出，任何一项变化自动产生新 revision，不需要单独维护项目头计数和授权版本号。
- 不做签名 manifest，不引入签名密钥。

## 2. 对象

| 对象 | 说明 | 现有对应 |
|---|---|---|
| Device | 一台机器，设备授权流登录时产生，可撤销 | `machines`，加 `revoked_at` |
| Binding | 设备上的一个工作目录绑定到若干项目。只存目录路径哈希和显示名，不存绝对路径 | 新增 `bindings` |
| Snapshot | 对一个 binding 解析出的完整清单 | 原 `GET /manifest` 的结果 |
| Revision | 清单规范化后的 SHA-256 | 新增 |

```
bindings
  id, org_id, user_id, device_id
  workspace_id    text    客户端算的路径哈希
  display_name    text
  project_ids     uuid[]
  applied_revision text   最近一次客户端上报成功应用的 revision
  state           enum(active, suspended, revoked)
  created_at, updated_at, last_sync_at
```

## 3. 接口

```
POST /v1/bindings
  {device_id, workspace_id, display_name, project_ids}
  → 校验每个项目的成员身份；返回 binding_id
  修改用 PATCH /v1/bindings/{id}，需 If-Match

GET  /v1/bindings/{id}/snapshot
  If-None-Match: "<revision>"
  304  未变化
  200  见 §4

GET  /v1/blobs/{sha256}
  返回内容字节。授权规则：该 sha256 被「此用户当前可见的某个资源版本」引用才放行，
  否则 404（不区分不存在与无权）。

POST /v1/bindings/{id}/sync-results
  {applied_revision,
   results: [{kind, name, action, detail}]}
  action ∈ installed | updated | removed | conflict_skipped | failed
  → 写入 distribution_logs，更新 bindings.applied_revision
```

**删除不单独下发：不在清单里就是该删。** 这只对完整清单成立。

## 4. Snapshot 结构

```json
{
  "revision": "sha256:…",
  "generated_at": "2026-09-11T08:00:00Z",
  "projects": [{"id": "…", "slug": "billing", "revision": "sha256:…"}],
  "policy": { "rules": {"enforced": ["security-baseline"]}, "hooks": {"autoApply": true}, "mcp": {"allowedHosts": ["*.corp.example"]}, "recall": {"enabled": false} },
  "grants": [{"group_key": "backend-pack", "name": "后端工具包"}],
  "resources": [
    {
      "kind": "skill", "name": "deploy-helper",
      "namespace": "billing", "level": "project",
      "version": 7, "version_id": "…",
      "sha256": "…", "size": 12345, "tags": ["deploy"],
      "files": [{"path": "SKILL.md", "sha256": "…", "size": 2048}],
      "status": "ok"
    },
    {
      "kind": "rule", "name": "naming",
      "status": "conflict",
      "conflict": {"projects": ["billing", "payments"], "versions": [3, 5]}
    }
  ],
  "limits": {"max_blob_bytes": 33554432, "max_snapshot_bytes": 1073741824, "max_entries": 5000}
}
```

- `namespace`：项目 slug、权限组 key，org 级为 `common`。客户端用它生成 `skills/<ns>/`、`claudemd/<ns>/`。
- `grants` + `projects` 用来生成 `manifest/roles.yaml` 和 `manifest/projects.yaml`。
- 资源级 `sha256` 是对 `files` 列表规范化后的哈希，用于快速判断整条是否变化。
- `status=conflict` 的资源不带 `files`，客户端保留旧快照中的版本。

## 5. 服务端计算流程

1. 校验：device 未撤销、binding 未撤销、用户未停用。
   **停用用户返回空 `resources`**，客户端据此卸载全部（沿用现有 D4 规则）。
   撤销的 device 返回 401。
2. 按[层级解析规则](./设计-资源类型与层级.md#4-解析规则)解析：org → team → project + 权限组，
   同键取最具体层级，同层冲突标 `conflict`。
3. policy 字段级合并。
4. 规范化：resources 按 (kind, name) 排序，字段固定顺序，JSON 无空白；对整个 snapshot
   除 `generated_at`、`limits` 外的部分算 SHA-256 作为 `revision`。
5. 与 `If-None-Match` 比较，相同则 304。

缓存键 `(user_id, sorted project_ids, 各项目 head, 用户授权最后变更时间)`；一期可不缓存。

## 6. 客户端侧约束（写给将来的 teamai 适配器）

- 下载到暂存区，逐文件校验 sha256，全部到齐后提升为不可变缓存目录 `<revision>/`。
- 物化到各工具目录时写 apply journal：目标路径、期望旧哈希、新哈希、状态。崩溃后按哈希恢复。
- 目标文件哈希既非旧值也非新值 → 用户改过 → `conflict_skipped`，不覆盖。
- 全部物化完成后才上报 `applied_revision`；上报失败不影响本地，下次重试。
- 401 → 设备已撤销：停止同步，本地文件保留，界面提示。**不承诺远程擦除。**
- 客户端从 `limits` 读取上限，不硬编码。

## 8. 已拍板

| # | 问题 | 决定 |
|---|---|---|
| 1 | 内容按文件哈希取，还是按资源打 zip | **按文件哈希**。适配器要 zip 可在服务端现打 |
| 2 | blob 走带鉴权直接下载，还是签名短链接 + 对象存储 | **直接下载**，内容继续存 PostgreSQL，部署形态不变 |
| 3 | 增量接口 `changes?cursor=` | **一期不做**，接口位置保留 |

## 9. 限制（初值，从 `limits` 下发）

| 项 | 值 |
|---|---|
| 单个 blob | 32 MiB |
| 单个 snapshot 解压后 | 1 GiB |
| 清单条目数 | 5000 |
| 文件路径 | 相对路径，禁止 `..`、绝对路径、符号链接、Windows 盘符与 UNC |
