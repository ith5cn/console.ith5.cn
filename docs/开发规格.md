## 1. 接口总表

前缀 `/v1`。旧 `/api/v1/*` 直接删除，不保留。

### 1.1 通用约定

| 项 | 约定 |
|---|---|
| 鉴权 | `Authorization: Bearer <access>`；access 15 分钟；refresh 轮换 + family 重用检测 |
| 租户 | 所有查询按 token 中的 org_id 过滤；跨租户对象一律 404 |
| 条件请求 | 可变对象返回 `ETag`。变更集与绑定的编辑**必须**带 `If-Match`（缺失 428，过期 412）；组织、策略、团队、项目、身份源、映射、审核人、标签的写接口 `If-Match` **可选**，带了且不符返回 412（ETag 是响应体的内容哈希） |
| 幂等 | 创建类写请求带 `Idempotency-Key`（客户端 UUID）；作用域 (org, user, method, route)；同 key 不同 body 返回 409 `IDEMPOTENCY_CONFLICT`；结果缓存 24 小时 |
| 分页 | 所有列表接口 `?limit=100&cursor=`；返回 `{items, next_cursor}`；limit ≤ 500；cursor 不透明，原样带回。审计事件用时间游标，其余用偏移游标 |
| 错误 | `{error: {code, message, request_id, details?}}`；code 见 1.9 |
| 请求 ID | 响应头 `X-Request-Id`，日志与审计携带 |
| 限流 | 按 user、device、org 三档令牌桶；超限 429 + `Retry-After` |
| 客户端版本 | 客户端带 `X-Client-Version`；低于 `/v1/capabilities` 的 `min_client_version` 返回 426 `CLIENT_UPGRADE_REQUIRED`；不带头放行（浏览器与脚本不受影响） |
| 指标 | `GET /metrics` Prometheus 文本格式：按路由模板的请求计数、耗时直方图、进行中数；`ITH5_METRICS_TOKEN` 非空时需 Bearer |

## 5. 员工侧

### 5.1 teamai-cli `server` 模式（正式路径）

补丁在 [contrib/teamai-cli/](../contrib/teamai-cli/)。`repo.kind = 'server'`：`teamai init --server <url> [--code]` 走设备流登录、
选项目、`POST /v1/bindings`、拉快照物化到 `<home>/team-repo`（与 git clone 相同布局，所有 ResourceHandler 不改）、种 AI 工具目录、
注入 hook、跑一次 pull。`pull` 在 `refreshTeamRepo` 里取快照（If-None-Match → 304）并按 journal 物化；`push` / `remove` 从 AI 工具目录
读源文件，上传 blob，建变更集并提交（碰到同资源的 draft / in_review 变更集则合并）；`contribute` 调 `/v1/learnings`；
会话结束与每次 pull 把 skill 用量、投票增量、会话摘要、按日用量发到 `/v1/reports/events`。成员机器上没有 Git。

### 5.2 Go 参考实现：`ith5-materialize`

teamai 有 `self` 单仓模式：团队资源放在业务仓库 `<repo>/.teamai/`，`teamai pull` 直接读磁盘，不走 git。
`ith5-materialize` 负责登录、绑定与两个方向的物化，teamai-cli 一行不改。它也是将来给上游写适配器的参考实现。

```
ith5-materialize login      --server https://… [--enroll 码]     设备授权流；先探 /v1/capabilities 校验版本
ith5-materialize projects                                         列出我有权限的项目
ith5-materialize bind       --project a[,b]                       当前目录绑定到项目
ith5-materialize sync       [--out .teamai] [--namespaced] [--force]
ith5-materialize push       [--title] [--project] [--level] [--fast-track] [--dry-run]
ith5-materialize contribute --title 标题 [--project] [--tags] 文件.md
ith5-materialize remove     --kind rule --name naming [--fast-track]
ith5-materialize unbind     [--purge]
ith5-materialize logout     [--purge]
```

**拉取（sync）**：取 snapshot（带 If-None-Match）→ 按 sha256 下载缺失 blob 到 `~/.ith5/blobs/` → 渲染 `.teamai/`
→ 按 journal 判断用户修改（哈希既非旧值也非新值就 `conflict_skipped`）→ 上报 sync-results。
快照缓存在 `.teamai/.ith5-snapshot.json`，journal 在 `.teamai/.ith5-journal.json`。

两种布局：
- **扁平**（默认）：`skills/<name>/`、`rules/<name>.md`、`learnings/<name>.md`。服务端已按绑定过滤，teamai 不需要选 role / project：`teamai init --self`。
- **分区**（`--namespaced`）：`skills/<ns>/<name>/`、`rules/<ns>/<name>.md`、`learnings/<ns>/<name>.md`，并写出 `manifest/roles.yaml`（每个权限组一个 role）
  与 `manifest/projects.yaml`（绑定的项目，其 skills / knowledge 命名空间包含 `common` 与全部授权组，所以选中项目即得到全部应得内容）。
  teamai 端 `init --self --project <slug>`。切换布局时清理旧布局文件后全量重来。

**推送（push）**：扫描 skills / rules / docs / agents / claudemd / culture 中哈希与 journal 不同的文件（env / hooks / mcp 是合并后的 YAML，不回推），
上传 blob → 创建变更集 → 提交。已在快照里的资源沿用原层级并带 `expected_prev_version`；新资源默认落到绑定的唯一项目，多项目时 `--project` 指定。
我名下已有 draft / in_review 变更集碰到同一资源时合并进去重新提交（对应 teamai push 的"更新已存在的 MR"）。`--fast-track` 在有发布权限时直接发布。

**contribute / remove / unbind / logout**：分别对应 `/v1/learnings`、只含 delete 的变更集、`DELETE /v1/bindings/{id}`、`POST /v1/auth/revocations`。
`--purge` 只删 journal 记录且哈希未变的文件，用户改过的一律保留。
