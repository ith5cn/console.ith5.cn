# 把客户端换成 teamai-cli 之后，平台变成什么样

一句话：不再自己写员工电脑上的那个命令行工具，改用腾讯开源的
[teamai-cli](https://github.com/Tencent/teamai-cli)。它本来就有"连企业后台"的模式。
我们的服务端只要多 4 个接口，管理后台、权限组、审计这些都留着。

| | 现在 | 改后 |
|---|---|---|
| 客户端 | 自己写的 Go 客户端 `ith5`，只支持 Claude Code，只能发 skill、command、agent | 员工装 `teamai-cli`，指向我们的服务器。支持 11 种 AI 工具、7 类内容，更新由腾讯维护 |
| 谁维护 | 服务端和客户端都自己维护 | 只管服务端 |

## 功能对比

| 维度 | 现在 | 改后 | 变化 |
|---|---|---|---|
| 支持的 AI 工具 | Claude Code | Claude Code、Codex、Cursor、CodeBuddy、OpenCode、Qoder 等 11 种 | 提升 |
| 能下发的内容 | skill、command、agent | skill、rule、CLAUDE.md 片段、MCP 配置、hook 规则、模型网关配置、Claude 插件 | 提升 |
| 权限组授权 | 管理员在后台配，服务端强制 | 同样由服务端算，客户端只执行 | 不变 |
| 版本与回滚 | 发布新版本指向旧内容，本地已有时零下载 | 回滚同样是下发旧版本，但客户端会重新下载 zip | 略降 |
| 撤权回收 | 停用账号后下次 sync 清理本机 | 停用账号后下次 sync 返回卸载命令，客户端照做 | 不变 |
| 审计 | Go hook 上报工具调用，不含内容 | 它的 hook 每次工具调用都会上报 cwd、工具名、会话状态。服务端入库前照旧丢掉提示词字段 | 不变 |
| 会话启动自动同步 | 需要员工手动 `ith5 sync` | 每次打开 AI 工具自动同步，员工无感 | 提升 |
| 个人屏蔽 | 无 | 员工可在本地屏蔽某个 skill，不影响他人 | 提升 |
| 项目级下发 | 只有用户级 `~/.claude` | 可下发到项目目录 `<repo>/.claude` | 提升 |
| 员工安装 | 一条 `curl \| sh`，无依赖 | 需要 Node 20，`npm i -g` | 下降 |
| Hook 延迟 | p95 2.8ms | 每次工具调用起一个 Node 进程，约 50 到 150ms | 下降 |
| 本机落盘 | 内容寻址 store + 软链，不碰用户文件 | 下载后复制，用清单文件记录归属，同样不覆盖用户自己的文件 | 略降 |
| 客户端维护 | 自己维护 1.3 万行 Go | 零维护。腾讯团队每周合十几个 PR | 提升 |
| 服务端维护 | 自己维护 | 自己维护，新增 4 个接口 | 不变 |

## 改后平台的优势

- **服务端说了算。** 这是它开源版本没有的东西。开源 teamai 靠 Git 仓库权限，谁都能选自己的角色。我们的平台是管理员配权限组，员工拿到的就是被授权的那份，停用账号自动回收。
- **一个后台管所有 AI 工具。** 公司里有人用 Claude Code、有人用 Cursor、有人用 Codex，内容发一次全覆盖。这是现在做不到、自己写也追不上的。
- **能管的东西多了一倍。** 企业最想统一的其实是 rule、MCP 服务器地址、模型网关。改后这些都能从后台下发，而且模型网关的 key 只落本机，不回传。
- **审计留着。** 谁、什么时候、在哪个仓库、用了什么工具，照旧记录。不记提示词，不记文件内容。
- **不用再养客户端。** 精力全部放在服务端治理上，这才是别人没有的部分。

## 要接受的代价

- **员工电脑要装 Node。** 安装从一条 curl 变成先装 Node 再 `npm i -g`。可以做一个安装脚本把这两步包起来。
- **Hook 变慢。** 2.8ms 变成几十毫秒，员工感知不到，但 README 里那个数字不能再写了。
- **协议不是他们的公开承诺。** 那 4 个接口是给腾讯内部平台做的，可能变。对策是锁定员工安装的版本，验证过再放开。

## 怎么用

### 管理员

和现在一样，全部在后台操作：

1. 上传或编辑内容，发布一个版本。除了 skill，现在还能发 rule、MCP、CLAUDE.md 片段。
2. 把内容放进权限组，把人授权到组。
3. 员工下次打开 AI 工具时自动拿到。后台能看到每个人实际装了哪些、哪个版本。
4. 要回滚就发布一个指向旧内容的版本。要收回就把人移出组或停用账号。
5. 审计页看谁在哪个仓库调用了什么工具。

### 员工

装一次，之后不用管：

```sh
npm install -g teamai-cli
teamai init --http https://console.ith5.cn/api --token <后台发的 key>
```

之后每次打开 Claude Code 或 Cursor，都会自动同步。常用命令：

| 命令 | 作用 |
|---|---|
| `teamai pull` | 立刻同步一次 |
| `teamai status` | 看当前装了什么 |
| `teamai skill exclude add <name>` | 本地屏蔽某个 skill |
| `teamai doctor` | 体检 |

> **token 从哪来。** 后台给每个人生成一个 API key，或者保留 `ith5 login` 做一个几百行的包装：
> 登录换 token，写进 teamai 的配置文件，再调 `teamai pull`。这层包装不碰它的代码。

## HTTP 模式用不到的功能，以及怎么补

HTTP 模式是"只读消费者"，下面这些用不上：

| 类别 | 具体 | 原因 |
|---|---|---|
| 只能靠 Git 仓库下发的内容 | agents、docs、env 环境变量、npm 包声明、角色 / 标签 / 项目清单、culture.md | HTTP 命令没有这些类型 |
| 写操作 | `push`、`contribute`、`remove`、`packages install`，以及 MR 提醒、摩擦分提醒、投票同步这几个 hook | 客户端在 HTTP 模式下直接拒绝 |
| 知识库 | learnings、`recall` 检索、代码图谱、`digest` 周报 | 都读 Git 仓库里的目录，HTTP 模式没有仓库。本机 `dashboard` 仍可用 |

**补法：混合模式，不改客户端代码。** 员工先用一个 Git 仓库做主仓，再把我们的服务端附加成 HTTP 源：

```sh
teamai init https://git.company.com/ai/team-repo                    # Git 主仓
teamai source add-http https://console.ith5.cn/api --token <key>    # 我们的服务端
```

两条线各管各的：

- **Git 仓库**管 agents、env、知识库、push / contribute、周报。走 MR 评审，适合团队自治的内容。
- **我们的服务端**管需要权限控制的 skill、rule、MCP、模型网关。停用账号就收回。

注意：Git 那条线不受权限组管，公司里"必须管住"的内容不能放那边。
建议先只走 HTTP，需要知识库的团队再叠加 Git 主仓。

## 更进一步：把 Git 那条线也收进后台

上一节的混合模式要员工另建一个 Git 仓库。如果想让后台管住全部功能，做法是**让服务端自己当 Git 服务**，
并模仿 GitLab 的几个接口。客户端仍然一行不改，它会把我们的服务端当成一个自建 GitLab。

### 客户端到底依赖什么

| 依赖 | 用途 | 我们要提供的 |
|---|---|---|
| Git 智能 HTTP 协议 | clone、pull、push 分支、force-push、孤儿分支 `teamai-reports` | Go 内嵌 Git 服务，按权限组暴露仓库地址 |
| `GET /users/sign_in` | init 时探测"这是不是 GitLab" | 返回一个带 GitLab 特征的页面 |
| `GET /api/v4/user` | 取当前用户名 | 按 token 返回用户 |
| `GET /api/v4/users?username=` | 解析 reviewer | 查用户 |
| `POST /api/v4/projects/:id/merge_requests` | `teamai push` 建 MR | 建一条"待审核"记录，返回 `web_url` |
| `GET /api/v4/projects/:id/merge_requests/:iid`（含 `/changes`、`/commits`） | MR 提醒、从 MR 导入知识 | 读"待审核"记录 |

### 后台变成什么

**后台是真相，Git 仓库是它的投影。**

- 管理员在后台编辑 skill / rule / agent / env / docs / MCP / hooks / culture，点发布，服务端生成一次 Git 提交。
- 一个权限组对应一个仓库地址，员工只能 clone 自己有权限的。这就是权限控制。
- 员工 `push` 上来的分支进"待审核"页，管理员看 diff、批准，服务端合并。
- 员工 `contribute` 的经验、`session save` 的周报数据、投票，客户端直接推进仓库；后台读出来做页面：知识库浏览、周报汇总、KB 健康度、learning 晋升。
- 审计仍由现有 Go hook 负责。Git 模式下 teamai 的 hook 不向服务端上报工具调用。

### 分期

| 期 | 做什么 | 拿到什么 |
|---|---|---|
| 一 | Go 内嵌 Git 服务；权限组投影成仓库；发布即提交 | 全部 11 类内容下发、多工具、自动同步、撤权 |
| 二 | 5 个 GitLab 接口；后台"待审核"页 | `push` / `remove` 走审批，MR 提醒 |
| 三 | 后台读仓库里的 learnings / sessions / teamwiki | 知识库浏览、周报、健康度、晋升 |

### 要说清楚的

- 一期是全新的数据模型（权限组投影、发布生成提交、分支变审核），比前面的 4 接口方案重得多。一个人做，三期合计是几个月。
- 前面的 HTTP 方案可以作为过渡先上线，一期完成后再切换。
- 客户端把"未知 host"探测成 GitLab 的逻辑可能随版本变，同样要锁定员工安装的版本。

## 服务端要做什么（HTTP 过渡方案）

1. **4 个接口。** `report` 收本机清单，`sync` 返回待执行命令，`ack` 收回执，`get-config` 给插件配置。都用 Bearer token 鉴权。
2. **一张命令队列表。** 对每个人每台机器，用权限组算出"应该有什么"，和 report 上来的"实际有什么"求差，差异变成 install / uninstall 命令。
3. **内容打包成 zip。** 命令里带一个签名下载链接，客户端拉下来解压。现有的内容存储和校验和照用。
4. **审计接进 sync。** sync 请求带 cwd、工具名、会话状态，按现有白名单提取后入库。提示词、transcript 路径这两个字段直接丢。
5. **后台加两个页面。** 内容类型多了 rule、MCP 等，发布页要能编辑；设备页要能看到每台机器的实际安装清单。

估计一到两周做完，用 teamai 的 `--http` 模式对着本地服务端跑通即可验收。

### 接口契约速查

客户端默认路径（可在其配置里覆盖）：

| 路径 | 方法 | 用途 |
|---|---|---|
| `/api/local-agent/report` | POST | 会话启动：上报 agent 类型、机器 ID、工作区、磁盘上实际安装的 skill / rule |
| `/api/local-agent/sync` | POST | 上报当前事件，返回 `{ ok, cmds: [...] }`（旧字段 `commands` 需同时返回以兼容） |
| `/api/local-agent/commands/ack` | POST | 回执 `{ id, status, error }` |
| `/api/local-agent/get-config` | POST | 插件配置 |
| `/api/projects/mine` | GET | 当前用户可绑定的项目列表 |

命令示例：

```json
{ "id": 1, "type": "install_skill", "skill_slug": "deploy-helper",
  "skill_version": "1.0.0", "download_url": "https://.../signed.zip" }
```
