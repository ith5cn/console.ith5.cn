# 运维：备份、恢复与数据保留

ITH5 的全部状态都在一个 PostgreSQL 库里，包括资源内容（`blobs` 表）。没有对象存储、没有本地文件目录、没有队列。
备份就是备份这个库，恢复就是把库还原后启动同一版本的二进制。

## 1. 备份

| 项 | 建议 |
|---|---|
| 方式 | 托管实例用自带的快照 + PITR；自建用 `pg_dump -Fc`，每日全量 |
| 频率 | 每日；发布高峰期可加 WAL 归档做到分钟级 |
| 保留 | 至少 30 天，覆盖去重账本窗口 |
| 校验 | 每月在临时实例上 `pg_restore` 一次，跑 `ith5-server -migrate` 确认迁移链完整 |

```sh
pg_dump -Fc "$ITH5_DATABASE_URL" -f ith5-$(date +%F).dump
```

`blobs` 表按 sha256 去重，内容体积通常远小于直觉；一个几百人的组织一年在几百 MB 量级。

除了库，还要保管两样东西：

- `ITH5_JWT_SECRET`：换了它所有令牌立即失效，成员需要重新登录（不丢数据）。
- 服务端二进制版本：恢复时用与备份时相同或更新的版本；迁移只前进不后退。

## 2. 恢复

1. 建空库，`pg_restore -d "$ITH5_DATABASE_URL" ith5-YYYY-MM-DD.dump`。
2. 用同一份 `ITH5_JWT_SECRET` 启动 `ith5-server`，迁移自动执行。
3. 打 `GET /healthz` 与 `GET /v1/capabilities`。
4. 让一台设备 `ith5-materialize sync --force` 确认快照能算、blob 能下。

恢复到较早时间点时，客户端本地 journal 里的 revision 可能"领先"于服务端；`sync` 会拿到旧 revision 的快照，
按哈希对比后回退到那一版，用户改过的文件照旧不覆盖。

## 3. 数据保留

| 数据 | 保留 | 谁清 |
|---|---|---|
| sessions、usage_daily、execution_events | 组织策略 `retention_months`（默认 13） | 每日维护任务 |
| report_events 去重账本 | 30 天 | 每日维护任务 |
| idempotency_keys | 24 小时 | 每日维护任务 + 写入时顺手删 |
| device_codes、过期或已撤销的 refresh_tokens、enrollments | 过期后 30 天 | 每日维护任务 |
| knowledge_votes、audit_events、distribution_logs、releases、bundle_versions、blobs | 不过期 | 不清；这是审计与回滚的依据 |

维护任务随服务启动，每 24 小时一轮；owner 也可在后台「组织策略 → 立即清理」或 `POST /v1/maintenance/run` 手动触发。
每轮结果写日志（各表删除行数、对账差异数、错误）。

## 4. 监控

- `GET /healthz`：ping 数据库，不通 503。
- `GET /metrics`：Prometheus 文本格式，按路由模板统计请求数、耗时直方图、进行中请求数。
  设置 `ITH5_METRICS_TOKEN` 后需要 `Authorization: Bearer <token>`；不设就只在内网暴露。
- 日志是 slog 文本，每条带 `request_id`，与审计事件里的 `request_id` 对得上。

建议告警：`ith5_http_requests_total{status=~"5.."}` 增速、`/healthz` 非 200、维护任务日志出现 `维护任务出错`。

## 5. 密钥与敏感数据

- 服务端只存 `password_hash`、`client_secret_enc`（IdP）、令牌哈希；原始密码与令牌不落库。
- 环境变量资源标记 `secret: true` 的没有值，值只在成员本机；内容库里不允许出现凭据，发布前逐文件扫描。
- 上报数据在解析阶段丢弃提示词、输出片段、绝对路径、完整命令行，库里没有这些列。

备份文件因此包含密码哈希与 IdP client secret 密文，仍按敏感数据保管。
