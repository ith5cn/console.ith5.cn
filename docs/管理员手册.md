# ITH5 管理员手册

面向负责维护公司 skill / command / agent 的人。

---

## 1. 三层模型

理解这三层，后面所有操作都是自然的：

```
内容（Bundle）      一个 skill、command 或 agent，有版本
    ↓ 装进
权限组               一组内容的具名集合，如「后端工具包」
    ↓ 授权给
人 / 项目 / 全组织
```

**为什么中间要有权限组？** 算一笔账（20 个后端、8 个后端专用内容）：

| 方案 | 授权条数 | 新人入职 |
|---|---|---|
| 直接把内容给人 | 20 × 8 = **160** | 手工点 8 次 |
| **用权限组** | **1** | **0，加入即全有** |

往组里加一个内容，所有被授权者下次同步自动拿到，**不需要改任何一条授权**。这是权限组存在的全部理由。

> 单个内容也可以直接授权给人——那条路留给「一次性/临时」场景，配合到期时间用。

## 2. 发布一个新内容

### 新建

**内容 → 新建**，四个字段：

| 字段 | 说明 |
|---|---|
| 名称 | 小写连字符。**这会成为 `/名称` 这个命令** |
| 类型 | `skill` = Claude 判断相关时自动调用；`command` = 只有用户敲 `/` 才触发；`agent` = 可被派发的 subagent（见下） |
| 说明 | 写进 frontmatter 的 `description` |
| 正文 | 可留空，会按类型自动种模板 |

**「说明」这个字段最值得花心思**——它不是给人看的注释，是 Claude 的调度依据。

```
❌ 「SQL 相关」                     太泛，会被乱调用
✅ 「审查 SQL 的性能风险。当用户提交 SQL、
    修改查询或询问慢查询时使用。」      说清「是什么」和「什么时候用」
```

点「创建并编辑」直接进编辑器。

### 三种类型分别落在哪

| 类型 | 落到员工机器上的位置 | 员工怎么用到它 |
|---|---|---|
| `skill` | `~/.claude/skills/<名称>/SKILL.md` | Claude 判断相关时自动加载 |
| `command` | 同上 | 员工敲 `/名称` |
| **`agent`** | **`~/.claude/agents/<名称>.md`** | 被 skill 按 `subagent_type` 派发 |

`agent` 是为了补一个洞：**subagent 只能定义在 `agents/` 目录下，没有办法塞进 skill 里**。
如果你发的 skill 会派发 subagent（比如一个编排型的开发流程 skill），那它依赖的
每个 agent 都得作为独立内容发出去，否则员工同步后那条路径必然失败——
而报错是「subagent_type 不存在」，他根本判断不出是配置没同步全。

### 写正文

**skill / command**：`SKILL.md` 是必须的。可以再加 `references/xxx.md` 之类的附属文件，Claude 按需读取。

**agent**：只有一个 `AGENT.md`，**不能带附属文件**——它在员工机器上就是一个 `.md`，没有目录能放别的东西。
正文的 `name:` **必须与内容名称完全一致**：

```markdown
---
name: corp-backend-engineer     ← 必须等于左边的内容名称
description: 后端开发 subagent。涉及 API、认证、服务端业务时派发。
---

你是后端工程师子 agent……
```

新建时留空正文的话，模板会自动把 `name` 填好。**但如果你后来改了内容名称，记得回来改这一行**——
派发用的是内容名称，两边对不上时 agent 装得上却永远派发不到，且员工那边看不出任何异常。
发布时会拦下这种情况。

写作要点：给**可执行的指令**，不要给描述。

```markdown
❌ 这个技能用于代码审查。

✅ 审查以下代码，重点检查：
   1. 错误处理是否完整
   2. 是否有资源泄漏
   发现问题时给出具体改法，不要只说「建议优化」。
```

### 发布

填变更说明，点「发布新版本」。

发布时会校验，不通过会说清原因：

| 拦截 | 原因 |
|---|---|
| 缺 `SKILL.md` | skill / command 必须有这个入口文件 |
| agent 不是「恰好一个 `AGENT.md`」 | 它落成单个文件，多出来的文件无处安放 |
| agent 的 `name` 与内容名称不一致 | 见上，会导致派发不到 |
| 缺 `description` | Claude 没法判断何时使用 |
| 路径含 `..` 或绝对路径 | 安全 |
| 名称是 `synced` | 该名被 Claude Code 保留 |
| 类型与 frontmatter 不一致 | 见下 |

> **类型不一致是什么意思**：选了 `command` 但正文没写 `disable-model-invocation: true`，那它**照样会被 Claude 自动调用**——类型就成了一句谎话。反过来选 `skill` 却写了这个字段，模型就调不到它。两个方向都会被拦下并说清后果。

**发布 ≠ 下发。** 发布只是产生一个新版本，没授权的人拿不到。

## 3. 把内容给到人

### 常规路径：加进权限组

**权限组 → 装配 → 勾选 → 保存。** 完事。

不需要碰授权页面——组早就授权给人了。

一个内容可以同时属于多个组（比如 `corp-git-规范` 既在后端包也在前端包），公用内容不必复制多份，改一处全部生效。

### 授权：三种主体

**授权 → 新增**：

| 授予给 | 用途 |
|---|---|
| 全组织 | 人人都该有的，如通用规范 |
| 指定成员 | 特定的人 |
| 项目 | 该项目成员 |

### 临时授权

新增授权时**设到期时间**。外包、实习、跨组支援用这个——到期自动失效，不用记得回收。

到期的条目在列表里标红但**保留行**，这是刻意的：留住审计可追溯性。

### 验证：授权解释器

改完授权后，进**授权解释器**选那个人，确认结果符合预期。

这一页排障时用得最多：

- **「他为什么能拿到这个？」** → 看「凭什么拿到」那列
- **「我授权了他为什么没有？」** → 不在列表里，再查内容是否未发布或已归档

## 4. 回滚

**内容 → 进入 → 版本历史 → 回滚到此版。**

它不是"把指针拨回去"，而是**用旧内容发布一个新版本**。这样设计有三个好处：

- 客户端永远不处理"降级"，逻辑简单不易错
- 审计里能看到「v4 是 v2 的回滚」（变更说明是自由文本，扛不了这个职责）
- 内容还在员工本地，**零下载**

## 5. 入职与离职

### 入职

1. 在**成员**页确认账号已存在
2. 把他加进对应的权限组授权（或该组已按项目/全组织授权，则无需任何操作）
3. 发给他：[员工上手.md](./员工上手.md)

### 离职

**成员 → 停用。**

他下次同步时会收到撤权信号，客户端自动清理本机内容、清空本地仓库与凭据。

> ⚠️ **准确的表述是「切断续期，不保证擦除」。**
>
> 清理动作依赖对方主动运行同步，而离职者通常当天就不再打开这台电脑。
> 真正有效的是下面这条内容规范。

---

## 6. 内容编写规范（强制）

**正文不得包含**：密钥与凭据、内部服务地址、客户数据、未公开的业务规则。

此类能力一律写成「调用服务端 API」的形态：

```markdown
❌ 当前定价规则：企业版 ¥X/座席/年，超过 50 座席打 7 折……

✅ 调用 https://api.corp/pricing-rules 获取当前定价规则并据此审查。
```

**为什么这条是强制的**：身份一撤，服务端 API 立即 401，本地残留的内容就是一具空壳。这是离职回收里**唯一不依赖客户端配合**的机制。

## 7. 审计：什么时候看哪个 tab

| tab | 答什么问题 | 什么时候用 |
|---|---|---|
| 分发记录 | 谁拿了哪个版本 | 追「这个问题影响了谁」 |
| **下发受阻** | 谁装不上、被什么挡住 | **运维时最先看这个** |
| 执行记录 | 谁用 AI 动了什么 | 采纳度、异常行为 |
| 长期未同步 | 谁掉了队 | 可能已离职未处理 |

三个 tab 都能导 CSV。

### 「下发受阻」为什么重要

员工本地已有同名内容时，我们**跳过、不覆盖**——绝不动用户自己的文件。但如果不记录这件事，「从未分配」和「一直装不上」在审计里长得一模一样，你永远发现不了。

看到条目后的处理：让该员工重命名或删掉自己的同名目录，再同步。

### 执行记录里有什么、没有什么

**有**：谁、何时、用什么工具、动了哪个仓库的哪个文件、改了几行、命令名。

**没有**：文件内容、diff、完整命令行、环境变量、提示词、模型响应。

所以你会看到 `执行 npm` 而不是完整命令行——参数里常有路径、URL 甚至凭据。

### 「长期未同步」怎么读

| 标记 | 含义 |
|---|---|
| **用户级** | 该成员**所有**设备都掉队 → 可能已离职未处理，优先跟进 |
| 设备级 | 部分设备掉队 → 通常只是换机或闲置 |

## 8. 排障

| 现象 | 排查 |
|---|---|
| 员工说看不到技能 | ① 授权解释器确认他应该有 ② 让他跑 `ith5 doctor` ③ 看「下发受阻」 |
| 装了但 Claude Code 里没有 | 大概率是首次安装后没重启 Claude Code。让他重启一次 |
| 某人一直装不上某个内容 | 「下发受阻」里看被什么路径挡住 |
| 改了内容员工没更新 | 确认**已发布**（不是只存了草稿）；让他跑 `ith5 sync` |
| 停用了但他本机还有 | 预期行为，见 §5 的说明 |
| `ith5 doctor` 报「系统策略冲突」 | IT 部署了 `managed-settings.json`，会让 hook 或技能静默失效，需要和 IT 协调 |

## 9. 部署

本地开发见 [README](../README.md)。上线要改五处：

| # | 项 | 生产要求 |
|---|---|---|
| 1 | `ITH5_JWT_SECRET` | ≥32 字节随机值，**进 secret manager** |
| 2 | 数据库 | 托管实例，改掉默认密码 |
| 3 | `ITH5_BASE_URL` | 真实 HTTPS 域名（会写进 `install.sh`） |
| 4 | TLS | **必须**——令牌在 Authorization 头里明文传输 |
| 5 | 演示数据 | 生产**不要**跑 `-seed` |

### 构建

```sh
cd web && npm ci && npm run build  # 必须在 go build 之前：产物要被编译进二进制
cd .. && go build -o ith5-server ./cmd/ith5-server
scripts/build-release.sh v1.0.0    # 各平台客户端二进制 + 校验清单 → dist/
```

### 部署目录布局

三样东西要一起上线，且**必须保持这个相对结构**：

```
/opt/ith5/
├── ith5-server
├── dist/            ← build-release.sh 的产物，员工下载的客户端二进制
└── scripts/
    └── install.sh   ← 运行时读取，不是编译进去的
```

`/install.sh` 这个路由是**运行时**去读 `<ITH5_DIST_DIR>/../scripts/install.sh` 的，
服务端只在下发时把 `__SERVER__` 替换成 `ITH5_BASE_URL`。

> ⚠️ **少了这两个目录不会导致启动失败**，只在日志里留一行 warn。表现是服务端看着一切正常、
> 管理后台也能用，但新人那条 `curl | sh` 拿到 404。同理，跳过 `npm run build` 直接
> `go build`，后台页面会 404 而 API 照常工作——**上线后务必实际跑一遍那条 curl 命令**。

### 启动

```sh
./ith5-server -migrate    # 可选：只跑迁移然后退出，用于单独确认迁移结果
./ith5-server
```

迁移 SQL 已编译进二进制，且**每次启动都会自动执行**，所以 `-migrate` 不是必需步骤。

服务端自身不做 TLS，挂在反向代理后面。探活打 `GET /healthz`，它会 ping 数据库，
不通返回 503。

之后把这条发给同事即可，服务端会自动把自己的地址填进脚本：

```sh
curl -fsSL https://你的域名/install.sh | sh
```

## 10. 这个产品做不到什么

务必对内对外都说清楚，别产生错误预期：

- 阻止开发者**读取或复制**已下发到本机的内容
- 阻止开发者**卸载** ith5
- **保证**离职者本机的文件被擦除
- 让 Cowork、云端会话、routines 用上分发的内容（这些场景不读本机技能目录）

**定位是治理与效率，不是安全管控。** 客户端控制不构成安全边界——这是 Claude Code 官方文档自己写的。定位说错了，第一次安全评审就会被否。
