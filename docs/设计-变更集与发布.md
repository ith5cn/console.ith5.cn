# 设计：变更集、审核与发布

> 状态：已定稿（2026-09-10）。对齐 Tencent/teamai-cli issue #341 与 PR #481 的领域模型，
> 套用到 ith5-server 现有的 bundle / bundle_versions 结构上。
> 目标是让本服务端成为 #341 的 Go 管理后端实现。

## 1. 为什么需要

现在的发布路径是：每个 bundle 一份 `draft_files`，管理员点发布直接生成新版本。
#341 要求把 Git 的 branch / MR / merge 翻译成后台概念：**草稿 → 审核 → 发布**，
且一次发布可以跨多个资源、多个项目原子生效。这需要一个独立的"变更集"对象。

## 2. 状态机

```
                 submit              approve              publish
  DRAFT ───────────▶ IN_REVIEW ───────────▶ APPROVED ───────────▶ PUBLISHED
    ▲                  │  │                    │
    │  request_changes │  │ reject             │ 内容或基线被改动
    └──────────────────┘  ▼                    ▼
                       REJECTED              DRAFT（审核作废）

  DRAFT / IN_REVIEW / APPROVED ──cancel──▶ CANCELLED
```

PUBLISHED、REJECTED、CANCELLED 为终态。要改，开新的变更集。

## 3. 数据模型

```
changesets
  id              uuid
  org_id          uuid
  author_id       uuid
  state           enum(draft, in_review, approved, published, rejected, cancelled)
  title           text
  description     text
  base_revisions  jsonb   {project_id: revision}  创建时锁定的基线；org/team 级用固定键
  submitted_digest text   submit 时对全部操作算的 SHA-256，冻结
  fast_track      bool    是否走快速通道（见 §6）
  release_id      uuid    发布后指向 releases
  etag            text
  created_at, updated_at

changeset_operations
  changeset_id    uuid
  seq             int
  op              enum(put, delete)
  level           enum(org, team, project)
  project_id      uuid    level=project 时必填
  team_id         uuid    level=team 时必填（Team 层落地后启用）
  kind            bundle_kind
  name            text
  blob_id         uuid    put 时必填，指向已校验的 blobs
  expected_prev_version int   可选：作者声明基于第几版修改

changeset_reviews
  id, changeset_id, reviewer_id
  decision        enum(approve, request_changes, reject)
  digest          text    审核时看到的 submitted_digest
  superseded      bool    digest 变化后置 true
  comment, created_at

releases
  id, org_id, changeset_id, published_by, published_at
  items           jsonb   [{bundle_id, version}]
  revisions       jsonb   {project_id: new_revision}

project_heads
  project_id      uuid PK
  revision        text
  release_id      uuid
  updated_at

blobs
  id, org_id, sha256, size, files jsonb, uploaded_by, created_at, referenced bool
```

规则：

- **删除必须显式**。`op=delete` 才删，"这次没带某个文件"不代表删除。
- **资源键**是 `(level, project_id, kind, name)`，不是文件名。
- blob 上传时校验声明的 sha256 与大小；未被任何变更集引用的 blob 到期清理。

## 4. 转换规则

| 转换 | 谁能做 | 服务端检查 |
|---|---|---|
| 创建 DRAFT | 有 `resource:write` | 目标项目的 base_revision 存在；每个 blob 已校验且属于同一 org |
| 编辑 DRAFT | 作者 | 需 If-Match；任何编辑清空已有审核并把 APPROVED 打回 DRAFT |
| submit | 作者 | 操作非空；算出 `submitted_digest` 并冻结 |
| approve / request_changes / reject | 有 `review:decide` 且**不是作者** | 审核记录携带 digest，与当前 `submitted_digest` 一致才生效 |
| publish | 有 `release:publish` | 见 §5 |
| cancel | 作者或 org 管理员 | 非终态 |

审核作废只有一条规则：**digest 变了，审核就无效**，旧审核标记 `superseded`。不设"审核过期"状态。

## 5. 发布：一个事务

1. 开事务，按 project_id 排序后逐个 `SELECT ... FOR UPDATE` 锁住目标项目的 `project_heads`。
2. 核对 `base_revisions` 与当前 head。
   - 全部一致 → 继续。
   - 有不一致 → 检查本变更集的操作与"基线之后发布的所有 release"是否触碰了相同的资源键。
     **互不重叠则自动放行**（重新以当前 head 为基线）；有重叠则整个发布拒绝，
     返回 `412 REVISION_MISMATCH` 并列出冲突的项目与资源键，变更集停在 APPROVED，作者重建。
3. 对每个 `put`：在对应 bundle 上插入 `bundle_versions`，`version = max + 1`。
   bundle 不存在则创建。单调整数版本模型不变。
4. 对每个 `delete`：插入一条 tombstone 版本（`files=[]`，`deleted=true`），同样占一个版本号。
   客户端看到 tombstone 即卸载。
5. 插入 `releases`，记录全部 `(bundle_id, version)` 与每个项目的新 revision。
6. 更新 `project_heads`，写审计事件（谁、何时、发布了哪个变更集、影响哪些项目）。
7. 变更集置 PUBLISHED，提交。

客户端只会看到旧 head 或新 head，不会看到中间态。

**Revision 的计算**：release 之后，取该项目"当前生效的全部 `(kind, name, version)`"按键排序，
拼接后 SHA-256。不透明、只比较相等、不可排序、不需要签名密钥。

**回滚**：一个新变更集，操作为若干 `put`，blob 指向历史版本内容，走同样的审核与发布。
生成的 `bundle_versions` 填 `rollback_of_version`。历史 revision 永不改写。

## 6. 已拍板的决策

| # | 问题 | 决定 |
|---|---|---|
| 1 | 管理员直接发布是否保留 | **保留快速通道**。有 `release:publish` 的人创建变更集时可带 `fast_track=true`，服务端仍生成完整变更集与 release 记录，跳过审核；审计中可见。贡献者仍不能审核自己的变更 |
| 2 | 审核人数 | **组织级配置 `required_approvals`，默认 1** |
| 3 | 能否部分批准 | **不能**。要拆就 request_changes 让作者拆成多个变更集 |
| 4 | 发布冲突谁处理 | **作者重建**。仅当操作与基线之后的 release 互不重叠时服务端自动放行 |

## 7. 与 teamai CLI 的对应

| CLI 行为 | 服务端 |
|---|---|
| `teamai push` 扫到 N 个改动 | 上传 N 个 blob → 创建 DRAFT（N 个 put）→ 立即 submit |
| push 时"更新已存在的 MR" | 作者已有 IN_REVIEW 变更集包含同名资源 → 编辑该变更集，不新建 |
| `teamai remove` | 只含 delete 操作的变更集 |
| MR 链接 | 后台变更集详情页 URL |
| MR 合并 | publish |
| 管理员后台编辑并发布 | 快速通道变更集 |

## 8. 与现有代码的关系

- `bundles.draft_files` 废弃，草稿统一进变更集。
- `bundle_versions` 表保留，新增 `deleted bool` 表示 tombstone。
- `adminPublish` / `adminRollback` 改为创建快速通道变更集后调用 publish。
- `internal/core/syncplan.go` 逻辑保留，输入改为按 `project_heads.revision` 取快照。
- 新增包：`changesets`（状态机与操作校验）、`releases`（发布事务与 revision 计算）、`blobs`。

## 9. 不做的

- 部分批准、服务端三方合并、跨组织原子发布。
- 签名 manifest：revision 由内容哈希导出，暂不引入签名密钥。
