# 设计：资源类型与层级

> 状态：已定稿（2026-09-10）。对齐 Tencent/teamai-cli 的资源格式与 issue #341 的层级模型。
> 配套：[设计-变更集与发布.md](./设计-变更集与发布.md)。

## 1. teamai 的资源形态

它的仓库里资源分三种形态，建模跟着形态走：

| 形态 | 资源 |
|---|---|
| 多文件目录 | skill（目录含 `SKILL.md`） |
| 单文件或单条记录 | rule（`rules/*.md`）、doc（`docs/**`）、agent（`agents/<name>.yaml`：name / description / instructions / model / tools）、claudemd 片段（`claudemd/<ns>/*.md`）、mcp 一个 server（`mcp/mcp.yaml` 中一条）、hook 一条声明（`hooks/hooks.yaml` 中一条）、env 一个变量（`env/env.yaml` 中一条） |
| 每层一份的单例 | `culture.md`、`teamai.yaml` 的 `sharing` 策略块 |

不是资源的：`tags.yaml`（资源上的标签）、`manifest/roles.yaml` 与 `manifest/projects.yaml`
（客户端选命名空间用，由服务端生成）、`sources`（订阅其他仓库，暂不支持）。

## 2. 资源类型

| kind | 形态 | 来源 | 说明 |
|---|---|---|---|
| `skill` | 目录 | 原 skill + 原 command | **command 并入 skill**，迁移时统一转换 |
| `rule` | 单文件 md | 原 standard | 改名 |
| `doc` | 单文件，允许子路径 | 新增 | name 即相对路径，如 `arch/overview.md` |
| `agent` | YAML 规格 | 原 agent（Claude md） | **以 teamai 的 YAML 为正本**，下发时按工具渲染；现有 md 做一次转换 |
| `hook` | 一条声明 + 可选脚本附件 | 原 hook（js） | 声明字段：id / event / matcher / command / timeout；脚本落到 team-scripts |
| `mcp` | 一个 server 定义 | 原 mcp | name / transport / command / args / url / headers / env / timeout |
| `env` | 一个变量 | 新增 | name 即 KEY，value + description；**一个变量一条资源** |
| `claudemd` | 单文件 md 片段 | 新增 | 注入各工具的 CLAUDE.md / AGENTS.md |
| `culture` | 单例 | 新增 | 每层最多一份，name 固定为 `culture` |
| `policy` | 单例 | 新增 | 对应 `sharing` 块：rules.enforced、hooks.autoApply / requireTeamScripts、mcp.allowedCommands / allowedHosts、recall.enabled、contributeHint.enabled、coAuthor.enabled |

**删除**：`workflow`、`setting` 两个 kind 及其数据，teamai 无对应概念。

**标签**：资源表加 `tags text[]`，任何 kind 可打；manifest 中原样返回，客户端按个人订阅过滤。

资源键：`(level, owner_id, kind, name)`。

## 3. 层级

新增 `teams` 表。项目可属于一个团队，也可直接挂在组织下。

```
org  →  team  →  project      （user 级本期不做）
```

表结构：

```
teams          id, org_id, name, slug, archived
team_members   team_id, user_id, role(member|admin)
projects       + team_id uuid NULL
project_members + role(member|admin)
bundles        level enum(org, team, project)
               team_id / project_id 按 level 二选一
               去掉 scope 字段（被 level 取代）
```

## 4. 解析规则

对一个绑定（用户 × 设备 × 若干项目）计算应得资源：

1. 取组织级全部资源。
2. 取这些项目所属团队的团队级资源。
3. 取这些项目的项目级资源。
4. 叠加权限组授予的资源（§5）。
5. 同一 `(kind, name)` 越具体的层级越优先：project > team > org > 权限组。
   下层的 tombstone 屏蔽上层同名资源；删掉 tombstone 后上层版本恢复。
6. 两个同时绑定的项目在同一层级给出同名不同版本的资源：报冲突，manifest 标记该键为
   `conflict`，客户端保留旧快照，不猜。
7. `policy` 不覆盖而是**字段级合并、取更严者**：
   - `rules.enforced`：并集，下层不能移除上层项。
   - `hooks.autoApply`、`mcp.autoApply`：上层 false 则下层不能改为 true。
   - `mcp.allowedCommands` / `allowedHosts`：上层非空时下层只能是其子集。
   - `recall.enabled`、`contributeHint.enabled`、`coAuthor.enabled`：下层可覆盖。
8. `culture`：取最具体层级的一份，不合并。

个人层的排除、标签订阅、env 本地覆盖留在客户端本地，服务端不参与。

## 5. 权限组的位置

两套机制并存、职责分开：

| 机制 | 决定什么 | 对应 teamai |
|---|---|---|
| 层级落点 | **谁必须拿到**。org 级全员，team 级团队成员，project 级项目成员 | `manifest/projects.yaml` 的项目命名空间 |
| 权限组 + 授权 | **谁额外拿到**。有名字的可选内容包，授权给用户 / 项目 / 组织，可到期 | `manifest/roles.yaml`：一个权限组 = 一个 role，其 namespace = 组的 key |

权限组内的资源仍有自己的层级落点（通常是 org 级），但**一旦被放进任一权限组，就不再按层级自动分发**，只经授权分发；否则 org 级的权限组内容会发给全员，权限组就失去意义。解析时权限组资源优先级最低。
现有 `permission_groups`、`permission_group_bundles`、`assignments` 三张表和
`internal/core/permissions.go` 的 Resolve 逻辑保留，作为第 4 步的输入。

## 6. 生成的兼容视图

服务端按绑定生成、随快照下发，客户端当作仓库文件读：

| 文件 | 生成自 |
|---|---|
| `teamai.yaml` | 合并后的 policy + 固定的 toolPaths |
| `manifest/projects.yaml` | 绑定的项目列表 |
| `manifest/roles.yaml` | 该用户被授权的权限组 |
| `tags.yaml` | 快照内资源的 tags 字段 |
| `skills/<ns>/<name>/`、`claudemd/<ns>/*.md` | ns = 项目 slug 或权限组 key；org 级用 `common` |
| `rules/`、`docs/`、`agents/`、`env/env.yaml`、`hooks/hooks.yaml`、`mcp/mcp.yaml`、`culture.md` | 对应 kind 合并后渲染 |

这些文件只是视图，不能反向当作授权依据。

## 7. 迁移

不需要。现有部署没有用户，`bundle_kind` 直接按 §2 定义，旧的 command / standard / workflow / setting
及其数据随旧结构一起删除。
