# ITH5 内部试点检查清单

试点的目的**不是验证功能能跑**——那些已经有测试和端到端验证了。目的是找出**我们俩都没想到的问题**：真人在真实环境里会卡在哪。

---

## 判定标准

试点算成功，当且仅当：

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | 每个人**独立**照文档装完，没来问你 | 数一下有几个人问了你 |
| 2 | 一周后他们**还在用**，没绕开 | 看「长期未同步」和执行记录 |
| 3 | 你改一次内容，所有人无感更新 | 发一版，第二天看分发记录 |
| 4 | 「下发受阻」为空，或有条目但你知道原因 | 看审计 |

**第 2 条最重要。** 装上不难，一周后还在用才说明这东西真的有价值。有人悄悄不用了，比报了个 bug 更值得追。

---

## 试点规模

| 项 | 建议 |
|---|---|
| 人数 | **2–4 人** |
| 挑谁 | 一个耐心的（会认真反馈）+ 一个不耐心的（会暴露体验问题）+ 一个不同平台的（Linux 或 Windows） |
| 时长 | **一周** |
| 内容 | 3–5 个**真的有用**的 skill，不要用 demo 数据 |

> 挑那个不耐心的人是关键。耐心的人会自己绕过问题然后不说，你什么也学不到。

---

## 试点前准备

- [ ] **清掉演示数据**——`demo` 组织和 `corp-*` 那些是我建的测试数据，别让试点者看到
- [ ] 建 3–5 个真实内容。从你们现在手工传的那些 skill 里挑最常用的
- [ ] 每个内容的 `description` 认真写（见《管理员手册》§2）
- [ ] 建一个权限组，把内容装进去，授权给试点者
- [ ] 用**授权解释器**逐个确认每人应该拿到什么
- [ ] 自己先完整走一遍《员工上手》，用一个干净的 HOME
- [ ] 服务端跑在**试点者能访问到的地址**上（不是 localhost）

---

## Day 1：装机环节

这是最容易卡人的地方。**让他们自己装，你在旁边看，别帮忙。**

### 观察点

| # | 观察什么 | 若发生 | 说明 |
|---|---|---|---|
| 1 | 有没有人卡在 `PATH` 提示 | 记下来 | 提示文案不够清楚，或该自动写 shell 配置 |
| 2 | **有没有人装完后没重启 Claude Code、以为坏了** | ⚠️ **重点** | 见下 |
| 3 | 有没有人平台检测失败 | 记下平台 | `install.sh` 要补该平台 |
| 4 | 有没有人校验和不匹配 | ⚠️ **立刻停** | 可能是构建产物不一致，也可能是传输被改 |
| 5 | `login` 的浏览器跳转是否顺畅 | 记下卡点 | 验证码输错、跳转失败都要记 |
| 6 | 装完到能用，**实际用了多久** | 计时 | 目标 5 分钟内 |

### 关于第 2 条

首次安装后需要重启一次 Claude Code，否则技能不出现。这是 Claude Code 的机制（会话启动时目录不存在就不会被监视），我们已经在 `install.sh` 里预建目录来规避，但**如果试点者在装 ITH5 之前就开着 Claude Code**，仍然要重启。

**如果有两个人以上卡在这里，说明文档写得不够醒目，要改。**

### 装完立刻让每人跑一次

```sh
ith5 doctor
```

十项应该全绿。任何一项红的都记下来。

## 第一周：日常使用

### 每天看一眼

- [ ] **执行记录**有没有数据 —— 没有说明 hook 没在跑，或者他们没在用
- [ ] **下发受阻**有没有新条目
- [ ] **长期未同步**有没有人上榜

### 中途做一次更新

第三天左右，改一个内容并发布。第二天看**分发记录**：

- 所有人都更新了 → ✅
- 有人没更新 → 问他，是没跑 sync 还是 sync 失败了

这一步验的是"改一次，所有人无感更新"这个核心承诺。

### 中途做一次权限组变更

往权限组里加一个新内容，**不改任何授权**。第二天确认所有人都拿到了。

这验的是权限组模型是否真的成立。

### 周末问三个问题

对每个试点者：

1. **这周有没有哪次你想用但没用？为什么？**
2. **有没有哪个技能被 Claude 乱调用了，或者该调用时没调用？**
3. **有没有任何一刻你觉得"这东西挺烦"？**

第 3 个问题最值钱。人不会主动说"烦"，要问。

---

## 信号 → 该改什么

| 信号 | 大概率原因 | 改哪里 |
|---|---|---|
| 多人卡在 PATH | 提示不够醒目 | `install.sh`，考虑自动写 shell 配置 |
| 多人没重启 Claude Code | 文档不够醒目 | 《员工上手》把这条提到最前面 |
| 有人 `doctor` 报**系统策略冲突** | IT 部署了 `managed-settings.json` | 找 IT 协调，这会让 hook 或技能**静默失效** |
| 有人落盘方式被探测成 `copy` | home 在网络盘或非 NTFS | 正常降级，但记下来确认它工作正常 |
| 「下发受阻」有条目 | 员工本地有同名内容 | 让他改名；同时考虑公司内容统一加 `corp-` 前缀 |
| 执行记录为空但人在用 | hook 没装上或被禁 | 让他跑 `doctor` 看「执行审计 hook」那项 |
| 技能被 Claude 乱调用 | `description` 写太泛 | 改 description，说清"什么时候用" |
| 该调用时没调用 | `description` 没覆盖那个场景 | 补 description，或改成 `command` 让人手动触发 |
| 有人一周没同步 | 忘了 / 觉得没必要 / 悄悄不用了 | **去问**，这是最值得追的信号 |
| 有人说"烦" | 具体听他说 | 可能要砍功能，不是加功能 |

---

## 试点期明确不要做的事

- ❌ **不要开会话追溯（M6）** —— 它还有两条前置没过（HR/法务、安全评审），而且试点期开它会污染你对"这东西好不好用"的判断
- ❌ **不要为了试点临时加功能** —— 试点是为了发现问题，不是为了让试点显得成功
- ❌ **不要帮他们装** —— 你一帮忙，装机环节的所有信号就没了
- ❌ **不要用演示数据** —— 假内容测不出 description 写得准不准

---

## 试点结束：三个决策

**1. 内容够不够用？**

如果试点者说"这几个技能没啥用"，那问题不在 ITH5，在内容。**先把内容做好再推广**——分发一堆没人用的东西，只会让人觉得这套系统是负担。

**2. 要不要买企业版？**

试点期如果遇到这些，就该认真算这笔账：

- IT 部署了 `managed-settings.json` 导致冲突
- 有人卸载了 ith5 而你发现不了
- 离职回收让你不放心

买 Claude Team/Enterprise 会同时解锁：server-managed settings（配置强制下发）、组织插件同步、以及**离职时移出组织即失效**——离职回收从"切断续期"升级成真正的失效。

**3. 推广还是先修？**

推广前应该满足：

- [ ] 判定标准四条全过
- [ ] 装机环节没有人卡住
- [ ] 「烦」的问题都有了处理方案
- [ ] 内容至少有 5 个是大家真的会用的

任一条不满足，**先修再推**。第一印象只有一次，一批人觉得这东西烦，后面很难扭回来。
